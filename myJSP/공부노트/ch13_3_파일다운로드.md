# ch13-3. 파일 다운로드

---

## 1. 왜 그냥 링크로는 안 되나

```html
<a href="storage/파일명">다운로드</a>
```
이렇게만 하면, 브라우저가 그 파일을 **열 수 있는 형식이면 새 탭에 그냥 열어버립니다** (이미지, PDF, txt 등). "다운로드 창"을 강제로 띄우려면 서버가 **"이건 내려받아야 하는 파일이다"라는 응답 헤더**를 붙여서 스트림으로 직접 흘려보내야 합니다. 그 역할을 하는 게 `fdownload.jsp`입니다.

## 2. 호출하는 쪽 — flist.jsp

```javascript
function down(upFile) {
    document.downFrm.upFile.value = upFile;   // 숨겨진 폼에 파일명 채우고
    document.downFrm.submit();                 // 그 폼을 제출
}
```
```jsp
<a href="javascript:down('<%=upFile%>')">다운로드</a>

<form name="downFrm" method="post" action="fdownload.jsp">
    <input type="hidden" name="upFile">
</form>
```

**왜 `<a href="fdownload.jsp?upFile=...">`로 바로 안 하고 굳이 숨겨진 폼 + JS를 거치나?**
- 파일명에 한글이나 특수문자(`&`, `공백` 등)가 있으면 URL 쿼리스트링에 그대로 넣었을 때 깨지거나 깨질 위험이 있음
- `POST` 방식 hidden input에 넣으면 URL 인코딩 걱정 없이 그대로 전달됨

## 3. 실제 전송 — fdownload.jsp

```jsp
<%@page contentType="application; charset=UTF-8"%>
<%
    String filename = request.getParameter("upFile");
    File file = new File(FileloadMgr.SAVEFOLDER + File.separator + filename);
    byte b[] = new byte[(int) file.length()];

    response.setHeader("Accept-Ranges", "bytes");
    String strClient = request.getHeader("User-Agent");
    if (strClient.indexOf("Trident") > 0 || strClient.indexOf("MSIE") > 0) {
        // 구형 인터넷 익스플로러
        response.setContentType("application/smnet;charset=UTF-8");
        response.setHeader("Content-Disposition",
                "filename=" + new String(filename.getBytes("UTF-8"), "8859_1") + ";");
    } else {
        // 그 외 모든 브라우저(크롬, 엣지, 파이어폭스...)
        response.setContentType("application/smnet;charset=UTF-8");
        response.setHeader("Content-Disposition",
                "attachment;filename=" + new String(filename.getBytes("UTF-8"), "ISO-8859-1") + ";");
    }
    out.clear();
    if (file.isFile()) {
        BufferedInputStream fin = new BufferedInputStream(new FileInputStream(file));
        BufferedOutputStream outs = new BufferedOutputStream(response.getOutputStream());
        int read = 0;
        while ((read = fin.read(b)) != -1) {
            outs.write(b, 0, read);
        }
        outs.close();
        fin.close();
    }
%>
```

## 4. 한 줄씩 분석

### 브라우저별 분기 — 왜 필요한가
```java
String strClient = request.getHeader("User-Agent");
if (strClient.indexOf("Trident") > 0 || strClient.indexOf("MSIE") > 0) { ... }
```
- `User-Agent` 헤더로 브라우저 종류를 짐작함 (`Trident`, `MSIE` = 인터넷 익스플로러 계열)
- **옛날 IE는 `Content-Disposition`에 `attachment;`를 안 붙여도 되고, 오히려 다르게 처리하는 버전이 있어서** 이런 분기가 필요했음. 지금은 IE가 사실상 서비스 종료된 브라우저라 **실무에서 이 분기는 점점 의미가 없어지는 추세**지만, 옛날 교재/실무 코드에서 왜 이런 분기가 있는지는 알아둘 필요가 있음

### 한글 파일명 처리
```java
new String(filename.getBytes("UTF-8"), "ISO-8859-1")
```
ch13-1에서 본 `getBytes("8859_1")` → `new String(..., "UTF-8")`와 **정반대 방향**입니다:
- 업로드 때(받을 때): "잘못 읽힌 걸 바로잡기" 위해 8859_1→UTF-8
- 다운로드 때(내보낼 때): HTTP 헤더 자체가 옛날 규격상 **ISO-8859-1만 안전하게 통과**시키기 때문에, UTF-8 바이트를 ISO-8859-1 문자로 "억지로 포장"해서 헤더에 실어 보냄 → 브라우저가 받아서 다시 원래 UTF-8로 해석

> HTTP 헤더는 원래 ASCII/Latin-1 기반으로 설계되어서, 한글 같은 비-ASCII 문자를 헤더 값에 넣으려면 이런 "바이트를 다른 문자셋인 척 포장"하는 우회가 필요합니다. 실무에서는 더 표준적인 방법(`filename*=UTF-8''인코딩된값` 형식, RFC 5987)을 쓰기도 하지만, 이 방식도 널리 쓰이는 실용적인 우회법입니다.

### 스트림으로 직접 전송 — 왜 이렇게 복잡하게 하나
```java
BufferedInputStream fin = new BufferedInputStream(new FileInputStream(file));       // 파일 → 읽기
BufferedOutputStream outs = new BufferedOutputStream(response.getOutputStream());   // 브라우저로 → 쓰기
int read = 0;
while ((read = fin.read(b)) != -1) {
    outs.write(b, 0, read);
}
```
파일 전체를 한 번에 메모리로 읽어서 보내지 않고, **버퍼 크기만큼씩 나눠서 읽고 바로바로 씀**. 파일이 아무리 커도(50MB든 5GB든) 메모리를 그만큼 다 잡아먹지 않고 흘려보낼 수 있음 — 이게 "스트리밍"입니다.

- `BufferedInputStream`/`BufferedOutputStream`: 매번 디스크/네트워크에 직접 왔다갔다 안 하고 버퍼에 모아뒀다가 처리 → 훨씬 빠름
- `fin.read(b)`: 버퍼(`b`) 크기만큼 읽고, 실제로 읽은 바이트 수를 반환 (파일 끝이면 `-1`)
- 다 쓰고 나면 **반드시 `close()`** — 안 닫으면 파일 핸들이 계속 열려있는 채로 남음 (리소스 누수)

> 이 코드엔 `close()`가 `try`에 없어서, 중간에 예외가 나면 스트림이 안 닫힐 수 있습니다. 정석대로면 `try-with-resources`(`try(var fin = ...; var outs = ...)`)를 쓰는 게 더 안전합니다 — ch09의 JDBC `finally { freeConnection(...) }` 패턴과 같은 이유입니다.

### `out.clear()` — 왜 필요한가
JSP는 기본적으로 텍스트(HTML) 응답 버퍼를 쓰는데, 우리는 **바이너리 파일**을 직접 스트림으로 쓸 거라서, 혹시 그 전에 뭔가 버퍼에 쌓인 게 있으면 지워서 순수하게 파일 바이트만 나가게 합니다.

## 5. 참고 — `contentType="application"` 은 표준이 아님

```jsp
<%@page contentType="application; charset=UTF-8"%>
```
`application`만 있고 서브타입이 없는 건 정식 MIME 타입이 아닙니다(보통 `application/octet-stream`을 씀 — "무슨 파일인지 모르니 그냥 바이너리로 받아라"라는 뜻). 실제로는 이후 `response.setContentType("application/smnet;charset=UTF-8")`로 덮어써지는데, `application/smnet`도 표준 MIME 타입은 아닙니다. **`Content-Disposition: attachment`가 이미 "무조건 다운로드해라"라고 지시하기 때문에, 대부분 브라우저는 정확한 Content-Type이 아니어도 다운로드는 정상 동작**합니다 — 다만 정석대로 하려면 `application/octet-stream`을 쓰는 게 맞습니다.
