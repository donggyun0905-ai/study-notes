## 1. ch08 — 서블릿 기본기 복습

### GET과 POST, 서블릿에서 받는 법이 다르다

```jsp
<%-- getJSP.jsp --%>
<form method="get" action="getServlet">
    msg: <input name="msg" value="오늘은 즐거운 화요일">
    <input type="submit" value="전송">
</form>
```
```java
// GetServlet.java
protected void doGet(HttpServletRequest request, HttpServletResponse response) {
    String msg = request.getParameter("msg");   // get이니까 doGet에서 받음
    ...
}
```

폼의 `method="get"`/`method="post"`에 맞춰 서블릿도 `doGet`/`doPost`로 나눠서 처리합니다. `request.getParameter(...)`로 값을 꺼내는 방법 자체는 GET이든 POST든 똑같습니다 — 다른 건 어디서 받는지(주소창에 노출되는 GET vs 안 보이는 POST)와 서블릿의 어느 메소드가 호출되는지뿐입니다.

### 서블릿 라이프사이클: init → service → destroy

```java
// ExServlet2.java
@Override
public void init(ServletConfig config) {
    System.out.println("init 호출");     // 서블릿이 최초 1번 로딩될 때만
}

@Override
protected void service(HttpServletRequest request, HttpServletResponse response) {
    System.out.println("service 호출");   // 요청이 올 때마다 매번
}

@Override
public void destroy() {
    System.out.println("destroy 호출");   // 서버 종료 또는 서블릿 갱신 시
}
```

`doGet`/`doPost`를 각각 만드는 대신 `service`를 오버라이드하면 GET이든 POST든 상관없이 요청을 한곳에서 다 받을 수 있습니다 (`ExServlet1`, `LogoutServlet`이 이 방식). 다만 GET/POST를 구분해서 다르게 처리하고 싶으면 `doGet`/`doPost`를 따로 쓰는 게 맞습니다.

### 세션 기반 로그인 — 서블릿 버전

```java
// LoginServlet.java
protected void doPost(HttpServletRequest request, HttpServletResponse response) {
    String id = request.getParameter("id");
    String pwd = request.getParameter("pwd");
    HttpSession session = request.getSession();
    if(id != null && pwd != null){
        session.setAttribute("idKey", id);      // DB 대조 없이 일단 세션에 저장만
    }
    response.sendRedirect("login.jsp");
}
```
```java
// LogoutServlet.java
protected void service(HttpServletRequest request, HttpServletResponse response) {
    HttpSession session = request.getSession();
    session.removeAttribute("idKey");
    session.invalidate();
    response.sendRedirect("login.jsp");
}
```

`ch12_2`(세션 로그인)에서 JSP로 했던 걸 이번엔 서블릿으로 그대로 반복한 것입니다. **로그인 상태를 서버에 남기는 방법은 결국 세션 하나뿐**이고, 그걸 JSP에서 만들든 서블릿에서 만들든 원리는 같다는 걸 다시 확인한 셈입니다. (참고: 이 버전은 아이디/비밀번호를 실제 DB와 대조하지 않는 단순 버전입니다 — 진짜 로그인 검증은 아래 ch14에서 다룹니다.)

## 3. 아이디 중복확인 — 두 가지 구현 방식

같은 기능(`duplicationId`)을 화면에 보여주는 방식이 두 가지 준비되어 있습니다. 원리를 먼저 팝업으로 배우고, 그다음 더 매끄러운 AJAX 방식으로 넘어가는 흐름입니다.

| | 방식 A (`member.jsp` + `idCheck.jsp`) | 방식 B (`member2.jsp` + `idCheck2.jsp`) |
|---|---|---|
| 호출 | `window.open()`으로 **새 창**을 열어서 결과 화면 자체를 보여줌 | `XMLHttpRequest`로 **페이지 이동 없이** 결과만 받아옴 |
| 서버 응답 | 완성된 HTML 페이지(Bootstrap 알림창) | `"duplicate"` 또는 `"available"` 텍스트 한 줄 |
| 사용자 경험 | 창이 하나 더 뜨고 직접 닫아야 함 | 폼 옆에 바로 초록/빨강 메시지 표시 (더 매끄러움) |

```jsp
<%-- idCheck.jsp : 결과 화면 자체를 팝업으로 --%>
<jsp:useBean id="mgr" class="ch14.MemberMgr"/>
<%
    String id = request.getParameter("id");
    boolean result = mgr.duplicationId(id);
%>
<%if (result) {%>
    <div class="alert alert-danger"><%=id%>는 이미 존재하는 ID입니다.</div>
<%} else {%>
    <div class="alert alert-success"><%=id%>는 사용 가능합니다.</div>
<%}%>
```

```js
// member2.jsp : AJAX로 결과만 받아서 폼 옆에 표시
var xhr = new XMLHttpRequest();
xhr.open("GET", "idCheck2.jsp?id=" + encodeURIComponent(id), true);
xhr.onreadystatechange = function () {
    if (xhr.readyState == 4 && xhr.status == 200) {
        var result = xhr.responseText.trim();
        if (result == "duplicate") { /* 빨간 메시지 */ }
        else { /* 초록 메시지 */ }
    }
};
xhr.send();
```

`ch09_5`(팀 이름 중복확인)에서 `fetch()`로 배운 것과 같은 원리를 `XMLHttpRequest`라는 더 옛날 방식으로도 구현해본 셈입니다 — **AJAX는 방법이 여러 개이고, 결국 목표는 "페이지 이동 없이 서버에 물어보고 결과만 받기"** 라는 게 핵심입니다.

## 4. 우편번호 검색 팝업 — 자식 창에서 부모 창 채우기

우편번호 검색은 `window.open()`으로 작은 팝업을 띄우고, 결과를 클릭하면 **팝업을 연 원래 화면(회원가입 폼)의 입력칸을 대신 채워주고 스스로 닫힙니다.**

```js
// zipSearch.jsp (자식 창)
function sendAdd(zipcode, adds) {
    opener.document.regFrm.zipcode.value = zipcode;   // 부모 창 폼의 우편번호 칸
    opener.document.regFrm.address.value = adds;       // 부모 창 폼의 주소 칸
    self.close();                                        // 팝업 자신을 닫음
}
```

`window.open()`으로 띄운 창에서는 `opener`라는 이름으로 자신을 연 부모 창(`window`)에 접근할 수 있습니다. `guestbook_3`의 `updateGuestBookProc.jsp`에서 `opener.location.reload()`로 부모 창을 새로고침했던 것과 같은 원리를 여기서는 "부모 창의 폼 필드 값을 채우는" 데 응용한 것입니다. 이 방식이 되려면 **부모 창 폼의 `name`(여기선 `regFrm`)과 팝업 코드에 적힌 이름이 정확히 일치**해야 합니다.

## 5. 회원가입 — 여러 개 선택하는 취미를 DB 한 컬럼에 담기

체크박스로 여러 개(인터넷/여행/게임/영화/운동)를 고를 수 있는데, DB엔 `char(5)` 컬럼 하나뿐입니다. **선택 여부를 5자리 0/1 문자열로 바꿔서 저장**하는 방식을 씁니다.

```java
// 저장할 때 — insertMember
String lists[] = { "인터넷", "여행", "게임", "영화", "운동" };
String hobby[] = bean.getHobby();          // 체크된 것만: 예) {"인터넷", "영화"}
char hb[] = {'0', '0', '0', '0', '0'};      // 기본값 전부 0

for (int i = 0; i < hobby.length; i++) {
    for (int j = 0; j < lists.length; j++) {
        if (hobby[i].equals(lists[j])) {
            hb[j] = '1';                    // 선택된 자리만 1로
            break;
        }
    }
}
pstmt.setString(9, new String(hb));         // "10010" 형태로 저장
```

"인터넷"과 "영화"를 고르면 `lists`의 0번·3번이라 `hb = {'1','0','0','1','0'}` → DB엔 `"10010"`. **읽어올 땐 반대로 한 글자씩 잘라서 복원합니다:**

```java
// 읽어올 때 — getMember
String hobby = rs.getString("hobby");        // "10010"
String hb[] = new String[hobby.length()];
for (int i = 0; i < hb.length; i++) {
    hb[i] = hobby.substring(i, i+1);          // "1","0","0","1","0"
}
```

`memberUpdate.jsp`에서 체크박스에 `checked`를 다시 채울 때 `hb[i].equals("1")`로 판단합니다. **저장할 때 쓴 `lists` 순서와 읽어올 때 배열 인덱스 순서가 정확히 같아야** 취미가 엉뚱하게 체크되는 일이 없습니다.

## 8. 오늘 정리

1. **서블릿이든 JSP든 로그인의 본질은 세션** — `session.setAttribute("idKey", ...)` 하나로 로그인 상태를 표시하고, `session.invalidate()`로 로그아웃하는 원리는 어디서나 동일.
2. **같은 기능도 구현 스타일은 여러 가지** — 아이디 중복확인(팝업 vs AJAX), 우편번호 데이터 소스(DB vs 파일) 둘 다 "같은 목적, 다른 방법"의 좋은 비교 사례.
3. **다중 선택 값은 고정 순서의 0/1 문자열로 인코딩**해서 DB 컬럼 하나에 압축 저장 — 저장 순서와 복원 순서를 반드시 맞춰야 함.
4. **자식 창 → 부모 창 통신은 `opener` 객체로** — `window.open()`으로 연 창은 항상 `opener`를 통해 자신을 열어준 창에 접근 가능.
