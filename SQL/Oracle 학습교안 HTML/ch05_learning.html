ERD — 데이터베이스 개체 설계도

테이블을 만들기 전, 개체(Entity)·속성(Attribute)·관계(Relationship)를 그림으로 설계하는 방법을 다룹니다. HR 스키마(EMPLOYEES/DEPARTMENTS 등)를 예시로 사용합니다.

00

ERD(Entity-Relationship Diagram)란

ERD는 개체(Entity)·속성(Attribute)·관계(Relationship) 세 가지 요소로 데이터베이스 구조를 그림으로 표현한 설계도입니다. CREATE TABLE을 작성하기 전, 테이블 간 관계와 제약조건을 먼저 시각적으로 정리하는 단계입니다.

요소의미SQL 대응
개체(Entity)독립적으로 관리되는 대상테이블(TABLE)
속성(Attribute)개체가 가지는 특성컬럼(COLUMN)
관계(Relationship)개체 간의 연결 방식외래키(FOREIGN KEY)
01

키와 제약 조건 — 개체 속성 표기법

표기법

개체 · 속성 다이어그램 기본 구조

개체는 사각형(테이블)으로, 속성은 그 안의 행(컬럼) 목록으로 표기합니다. 표 상단에는 개체 이름(테이블명), 각 행에는 속성명과 자료형을 적습니다.

표기 규칙 — 밑줄(underline)이 그어진 속성은 기본키(PK), PK/FK 태그는 왼쪽에, 자료형은 오른쪽에 배치하는 것이 일반적인 관례입니다. NN=NOT NULL, UK=UNIQUE 제약을 함께 표시하기도 합니다.
키

기본키(Primary Key, PK)

한 테이블에서 각 행을 유일하게 식별하는 속성(들)입니다. NULL을 허용하지 않고, 값이 중복될 수 없습니다. ERD에서는 속성 이름에 밑줄을 긋거나 PK 태그로 표시합니다.

CREATE TABLE employees(
  employee_id NUMBER(6) PRIMARY KEY,  -- 단일 컬럼 PK
  ...
);
복합키(Composite PK) — 두 개 이상의 컬럼을 묶어 PK로 지정할 수도 있습니다. 예를 들어 ch09에서 다룬 PRIMARY KEY(num, name)처럼, 각 컬럼은 개별적으로 중복 가능하지만 조합은 유일해야 합니다. ERD에서는 두 속성 모두에 밑줄을 긋습니다.
키

외래키(Foreign Key, FK)

다른 테이블의 기본키를 참조하는 속성으로, 두 테이블 사이의 관계를 연결하는 역할을 합니다. ERD에서 FK는 관계선이 연결되는 지점의 속성이며, 태그로 FK를 표시합니다.

CREATE TABLE employees(
  employee_id   NUMBER(6) PRIMARY KEY,
  department_id NUMBER(4),
  CONSTRAINT emp_dept_fk FOREIGN KEY(department_id)
      REFERENCES departments(department_id)
);
FK와 PK의 관계 — EMPLOYEES.department_id는 DEPARTMENTS.department_id(PK)를 참조하는 FK입니다. ERD 다이어그램에서 이 관계는 두 사각형(테이블) 사이를 잇는 선으로 시각화됩니다 (2절에서 다룸).
키

후보키(Candidate Key) · 대체키(Alternate Key)

후보키는 "PK가 될 자격이 있는" 유일성·최소성을 만족하는 속성(들)의 집합입니다. 여러 후보키 중 하나가 PK로 선택되면, 나머지는 대체키가 됩니다.

용어설명EMPLOYEES 예시
후보키(Candidate Key)PK가 될 수 있는 모든 후보employee_id, email
기본키(Primary Key)후보키 중 실제 선택된 것employee_id
대체키(Alternate Key)선택되지 않은 나머지 후보키email
실무 연결 — 대체키는 보통 UNIQUE 제약으로 구현됩니다. ch01 DDL 예제의 emp_email_uk UNIQUE(email)가 바로 email을 대체키로 강제한 예입니다.
제약조건

NOT NULL / UNIQUE — 속성 레벨 제약

PK·FK 외에도 개별 속성에 걸 수 있는 제약조건들이 있으며, ERD에서는 속성 옆에 약어로 표기하는 것이 일반적입니다.

제약조건ERD 표기의미
NOT NULLNN값이 반드시 있어야 함(빈 값 불허)
UNIQUEUK테이블 내에서 값이 중복되면 안 됨(NULL은 허용)
CHECKCK지정한 조건식을 만족해야 함 (예: salary>0)
PK vs UNIQUE 차이 — PK는 "NOT NULL + UNIQUE"가 자동으로 합쳐진 것이며 테이블당 1개만 가능합니다. UNIQUE 제약은 NULL을 허용하고 여러 컬럼에 개별로 지정할 수 있습니다.
02

관계 — 개체 관계 표기법

표기법

Crow's Foot(까마귀 발) 표기법 — 기호 정리

관계선 끝에 붙는 기호로 "몇 개까지 연결될 수 있는지(기수성, Cardinality)"와 "반드시 있어야 하는지(선택성, Optionality)"를 동시에 표현합니다. 가장 널리 쓰이는 표기법입니다.

1:1

1:1 관계 — 일대일

한 개체의 인스턴스 1개가 다른 개체의 인스턴스 정확히 1개와만 연결됩니다. 실무에서는 자주 등장하지 않으며, 보안·성능상 테이블을 분리할 때 주로 사용됩니다.

예시 — 직원(EMPLOYEES) 1명은 사원증(EMP_BADGE) 정확히 1개만 발급받는 경우처럼, 두 개체가 서로 정확히 1개씩만 대응하는 관계입니다.
1:N

1:N 관계 — 일대다 (가장 흔한 관계)

한쪽(1) 개체의 인스턴스 1개가 다른 쪽(N) 개체의 여러 인스턴스와 연결될 수 있는 관계입니다. FK는 항상 "다수(N)" 쪽 테이블에 위치합니다.

예시 — 부서(DEPARTMENTS) 1개에는 여러 직원(EMPLOYEES)이 소속될 수 있지만, 직원 1명은 부서 1개에만 속합니다. HR 스키마에서 가장 많이 등장하는 관계 유형입니다.
N:M

N:M 관계 — 다대다 (교차 테이블 필요)

양쪽 개체 모두 서로 여러 인스턴스와 연결될 수 있는 관계입니다. 관계형 DB는 N:M을 직접 표현할 수 없으므로, 중간에 교차 테이블(연결 테이블, Junction Table)을 두어 두 개의 1:N 관계로 분해합니다.

구조 분석 — 학생(STUDENTS) 1명은 여러 과목(COURSES)을 수강하고, 과목 1개도 여러 학생이 수강합니다. 이를 풀기 위해 ENROLLMENTS(수강신청) 테이블을 만들고, 그 안에 student_id·course_id 두 개의 FK를 두어 1:N + N:1 구조로 분해합니다.
실무 팁 — 교차 테이블의 PK는 흔히 두 FK를 묶은 복합키(PRIMARY KEY(student_id, course_id))로 지정합니다. 1절에서 배운 복합키 개념이 여기서 실제로 쓰입니다.
식별/비식별

식별 관계 vs 비식별 관계

FK가 자식 테이블의 PK에 포함되는지 여부에 따라 두 가지로 나뉩니다. ERD에서는 관계선을 실선/점선으로 구분해 표기합니다.

구분선 표기의미예시
식별 관계(Identifying)실선(——)부모의 PK가 자식의 PK 일부가 됨 → 자식은 부모 없이 존재 불가ENROLLMENTS(student_id+course_id가 곧 PK)
비식별 관계(Non-Identifying)점선(- - -)부모의 PK가 자식의 일반 속성(FK)으로만 들어감 → 자식이 독립적으로 존재 가능EMPLOYEES.department_id (직원은 부서 배정 없이도 존재 가능, NULL 허용 시)
판별법 — "자식 레코드가 부모 없이 의미를 가질 수 있는가?"를 자문해보면 쉽습니다. 수강신청 기록은 학생·과목 없이는 존재 의미가 없으므로 식별 관계, 직원은 부서가 미정이어도(NULL) 직원 그 자체로 의미가 있으므로 비식별 관계입니다.

확인 문제 (셀프 체크)

1PK와 UNIQUE 제약조건의 차이를 2가지 이상 설명하시오.

2JOB_HISTORY 테이블(ch01 HR 스키마)의 PK가 (employee_id, start_date) 복합키인 이유를 설명하시오.

3학생-과목처럼 N:M 관계를 데이터베이스에 직접 구현할 수 없는 이유와 해결 방법을 설명하시오.

4EMPLOYEES-DEPARTMENTS 관계가 식별 관계인지 비식별 관계인지 판단하고 근거를 드시오.

정답 힌트 — 1번은 개수 제한(테이블당 PK 1개 vs UNIQUE 여러 개)과 NULL 허용 여부, 2번은 "한 직원이 여러 번 직무 이력을 가질 수 있으므로 employee_id만으로는 유일성이 보장되지 않는다"는 점, 3번은 관계형 모델의 한계와 교차 테이블, 4번은 department_id가 NULL을 허용하는지(비식별) 여부로 판단합니다.
